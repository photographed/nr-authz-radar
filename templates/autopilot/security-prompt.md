# Autopilot 用セキュリティ・トリアージのプロンプト

`templates/workflow-automation/security-triage.yaml` の `askAutopilot` に埋め込んでいるプロンプトの説明版。**変更するときは両方を揃える。**

## 前提
- Autopilot には上限がある（1組織あたり1時間100リクエスト）。**CRITICAL の Issue だけ**をこのプロンプトに渡す。CRITICAL は証拠の強さが「証拠」の検知（D01・D07）に限っているので、呼び出しは少なく、空振りもほぼ無い。
- Autopilot は推奨のみで、操作は実行しない。ブロック・トークン失効・WAF の変更は人の承認で行う。
- Knowledge に `templates/knowledge-runbooks/` を登録しておくと、Autopilot が調査中に参照する。

## プロンプトのルール
1. **2つの節に分ける**: 「今のデータでわかること」（確認した事実と、実行したクエリ）と「推奨」（次の作業。影響の大きい操作は承認が必要と明記）。
2. **攻撃か、自分たちの変更か**を判断する。
   - iRCA が有効なら、その結果を使う。トポロジーの内部に原因（デプロイ・資源の上限）があれば自分たちの変更の可能性が高い。内部に原因が無ければ外部からの入力の可能性が高い。
   - iRCA が無効なら、直近2時間のデプロイと異常の開始時刻を比べる。
   - 認可属性の挙動がデプロイの直後に変わったなら、**認可チェックの欠落**を疑う。
3. **「AI エージェントによる攻撃」と断定しない。** 「自動化らしい挙動」として根拠とともに書く。
4. **個人データを書かない。** ユーザー ID・IP アドレス・メールアドレスの生の値は使わず、件数や仮名化された ID を使う。
5. **わからないことは「不明」と書く。** サンプリング・保存期間・属性の不足などの理由と、何があれば埋まるかを添える。
6. Issue のタイトルにある検知 ID（例: D01）のランブックへのリンクを付ける。アラート条件の説明に ATT&CK の技術 ID があれば、そのまま添える（新たな技術を推測で足さない）。
