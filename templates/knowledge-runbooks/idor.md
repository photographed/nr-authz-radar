# ランブック: IDOR / BOLA（D01・D02・D03）

## 意味
- **D01**: 他人のリソースを **返した**（`owner_match = false` かつ `allow`）。情報漏えいの可能性がある。**最優先**。
- **D02**: 他人のリソースへのアクセスを **拒否した**。防げているが、同じ相手が守られていない別の API を探している可能性が高い。
- **D03**: 1ユーザーが短時間に多数の異なる ID にアクセスした。列挙の可能性。他人のデータだったかは、D01 が無いと分からない。

## 最初の15分（今わかることを集める）
1. 対象の API（トランザクション名）と、対象ユーザー（仮名化 ID）を確認する。
2. 開始時刻と、その前後のデプロイを確認する（D18。iRCA が有効ならその結果）。
3. 対象ユーザーのタイムライン（I01）と、触った API（I02）を見る。
4. D01 なら、200 で返ったリソースの範囲を確認する（I03）。**サンプリングの有無（I05）も必ず確認**する。

## 判断
| 状況 | 見立て |
|---|---|
| D01 がデプロイ直後から発生 | 認可チェックの欠落（自分たちの変更）。ロールバックを検討 |
| D01 がデプロイと無関係に、特定のユーザーから | 既存の脆弱性を突かれている |
| D01 が管理・サポート業務の時間帯に | 正当なアクセスの可能性。`bypass-authorities` の設定漏れを確認 |
| D02 だけ | 防げている。D03・D04 と合わせて探索の範囲を確認 |

## 封じ込め（承認が必要）
- 該当バージョンのロールバック、または該当 API の一時停止
- 対象アカウントのセッション・トークンの失効
- WAF でのレート制限

## ④ 調査へ
D01 が出たら、情報漏えいの可能性として ④ 調査（I01〜I07）を始める。APM は手がかり、**ログで全件を確定**させ、結果を保全する。
個人情報の漏えいに当たる可能性がある場合は、社内の手順に従って関係部署に連絡する。

## 誤検知
- 共有・委任の機能（家族アカウント、チーム共有など）で、所有者以外が正当に見られる → `ownerId()` の判定を見直す
- 管理者・サポート → `bypass-authorities` に追加する

## 再発防止
- コード監査（`api-authz-review`）の F4 を修正し、IDOR の回帰テスト（ユーザー A が B のリソースを取得すると 403 / 404）を追加する
- Java なら `@CheckOwnership` を ENFORCE モードにする
