# Errors Inbox・Performance Risks Inbox との連携（設計）

> **状態: 設計のみ。データの取得は未実装。**
> どちらも、データの取り出し方（NerdGraph の API・Ground Truth MCP のツール）を実際の New Relic アカウントで確認できていないため、
> 推測で実装しない。確認できたら下の「実装の手順」に沿って実装する。

## なぜ連携するのか
どちらも **偽陽性を減らす** 方向に効く。

| 機能 | 効き方 |
|---|---|
| Errors Inbox | 人がエラーグループに付けた判断（無視・解決済み）を、検知の結果に反映できる。**人の判断が偽陽性の除外に生きる** |
| Performance Risks Inbox | コード監査の Finding が、本番で実際に起きている形（大きな応答・大量のクエリ）かを裏付けられる |

## 1. Errors Inbox

### 今の状態
元データの `TransactionError` を NRQL で見ている（D06 DB 構文エラー、D17 新しい例外、D21 RCE の試み）。エラーグループの状態は見ていない。

### 使う情報
エラーグループ（同じ種類のエラーをまとめたもの）の、状態（未対応・解決済み・無視）、最初と最後に出た時刻、件数、担当者。

### 判定への反映
| エラーグループの状態 | D06・D17・D21 の扱い |
|---|---|
| 未対応で、**最初に出た時刻が調査の期間内**（新しいグループ） | 証拠の強さはそのまま。「新しく出た」と報告する |
| **無視**（人が「問題ない」と判断した） | 強さを「参考」に下げ、「既知（無視に設定済み）」と書く。攻撃の兆候として数えない |
| **解決済みなのに再発** | 「再発」として報告する（直したはずの箇所に、また攻撃の入力が届いている可能性） |
| 以前から未対応のまま | 強さはそのまま。「既知・未対応」と書く |

### 書き込みはしない
プラグインの方針（読み取りのみ・生成のみ）どおり、Errors Inbox への担当者の設定やコメントは **しない**。
代わりに、コメントの文案と担当の候補をレポートに書き、人が貼り付ける。

### エラーグループとの対応付け
検知の結果の行（`transactionName`・`error.class`）と、エラーグループを、`error.class` とトランザクション名で対応付ける（エラーグループの集約の単位は要確認）。

## 2. Performance Risks Inbox

### 検出されるリスク（公開情報より）
N+1 クエリ、遅い SQL、DB クエリ過多、順次実行の DB クエリ、遅い HTTP リクエスト、大きな HTTP の応答。

### セキュリティの観点での読み替え
| リスク | セキュリティでの意味 | 使い方 |
|---|---|---|
| **大きな HTTP の応答** | 過剰なデータ露出（F8・API3）、一覧やエクスポートでの大量取得 | 同じエンドポイントに F8 があれば **裏付けあり** と書く |
| **トランザクションあたりの DB クエリ過多** | 1回のリクエストでの大量取得（GraphQL のエイリアス、バッチ）。**D23 を計装なしで近似** できる | 異常の兆候として扱う（攻撃とは書かない） |
| N+1 クエリ | 一覧の API が子のデータを1件ずつ読んでいる。Entity をそのまま返す API（F8）であることが多い | F8 の参考 |
| 遅い SQL | 多くは性能の問題。**新しく出た** 場合だけ、時間差を使う SQLi（D09）と合わせて見る | 参考 |
| 順次実行の DB クエリ・遅い HTTP リクエスト | セキュリティとの関係は薄い | 使わない（遅い外部呼び出しの宛先が新しい場合だけ D20 の参考） |

### 優先度への反映
点数は変えない（裏付けは「本番でその形が起きている」ことを示すだけで、悪用できることは示さないため）。
レポートの Finding に「本番での裏付け: 大きな応答（Performance Risks Inbox）」と書き、同じ段階の中で先に並べる候補にする。
