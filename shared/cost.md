# コストとトークン

このプラグインのコストは **New Relic 側**（クエリ・アラート・Autopilot・Ground Truth）と **Claude 側**（トークン）の2つ。
どちらも「AI を使わなくてよい処理は決まったスクリプトで行い、AI には要約だけを読ませる」設計で抑えている。

> 料金体系は契約によって異なり、この環境からは New Relic の料金ページを確認できていない。
> 下の「確認すべきこと」を New Relic の担当者に確認すること。

## 1. New Relic 側

### 使い分け（既定の方針）
| 用途 | 使うもの | AI | 理由 |
|---|---|---|---|
| 定期の Hunt・前提の確認 | **`scripts/hunt.py`（NerdGraph で NRQL を直接実行）** | 使わない | 決まった処理で毎回同じ結果。API キーで動くので無人実行もできる |
| 対話での調査・深掘り | Ground Truth MCP の **NRQL を実行するツールだけ** | Claude のみ | 必要なときだけ。分析系の AI ツールは使わない |
| 有事の調査 | Autopilot（有効な場合） | 使う | **CRITICAL（証拠の強さが「証拠」）のアラートからだけ**呼ぶ |

### Hunt のクエリ数（`hunt.py --dry-run` で実測）
| 段階・データソース | 全部 | `--levels evidence,strong`（軽量） |
|---|---|---|
| S0（データソースなし） | 6 | — |
| S0 + Span | 9 | — |
| S2 + Span | 14 | — |
| S3 + Span・Browser・デプロイ記録 | 21 | 7 |

21本のうち **9本が重いクエリ**（Span を読む、平常時と比較する `COMPARE WITH`、入れ子のクエリ）。最も重いのは D20（Span を30日分。宛先を200件までに制限済み）。

**推奨の頻度**: 毎日は軽量（`--levels evidence,strong`）、週1回は全部。異常の検知は週1回で十分なことが多い。

### ログ
- **スキャンしない。** ログへのクエリは L01〜L04 だけで、どれも APM の手がかり（トレース ID・ユーザー）か明示的なフィルタ、短い時間の範囲、件数の上限（200 以下）で絞っている（テストで確認）
- `hunt.py`（定期の Hunt）はログを読まない
- 取り込みは最小限を推奨（アクセスログとセキュリティ関連のアプリのログ）。ログの取り込み量はコストに直結する

### アラート
- 既定で生成するのは **証拠と強い兆候だけ**（S3 でも6本）。異常の検知は `--include-anomaly` を付けたときだけ、通知しないポリシーに入る
- アラート条件の評価がどう課金されるかは契約による（要確認）

### Autopilot
- 利用には Pro / Enterprise と Advanced Compute アドオンが必要（確認済み）。上限は1組織あたり1時間100リクエスト
- 呼ぶのは CRITICAL（D01・D07）だけなので、通常はほとんど呼ばれない。定期の Hunt や Skill からは呼ばない

### Ground Truth MCP
- 料金は未確認。AI を使う分析系のツールと、NRQL を実行するだけのツールで扱いが違う可能性がある
- ツールはカテゴリ（discovery・data-access・alerting・incident-response・performance-analytics・advanced-analysis）に分かれていて、**ヘッダーで使うカテゴリを絞れる**（確認済み）。**data-access と discovery だけに絞る** のを推奨する（ヘッダー名と書き方は公式ドキュメントで確認）

### 確認すべきこと（New Relic の担当者に）
1. 自社の料金体系（compute ベースか）で、NRQL のクエリ・アラート条件の評価・NerdGraph 経由のクエリが、それぞれどう課金されるか
2. Ground Truth MCP の課金（ツールの種類による違いの有無）
3. Autopilot の課金単位
4. Span・Transaction のデータ保持期間と、長期間を読むクエリ（D20 など）のコスト

## 2. Claude 側（トークン）

### 仕組み
| 仕組み | 内容 | 実測（バイト数） |
|---|---|---|
| **短い SKILL.md** | Skill を呼ぶたびに読まれるので、手順の入口だけにした。詳細は必要なときだけ読む参照ファイルへ | 2つの SKILL.md: **24.5KB → 9.4KB** |
| **`catalog.py`** | クエリの一覧（1行1件）と、必要な ID の節だけを出す | 一覧 **2.4KB**（4つの参照ファイルは **40.7KB**）。D01 の節だけなら約0.5KB |
| **`hunt.py` の要約** | 全クエリの結果を、証拠の強さごとの短い表にまとめる。Claude は要約だけを読む | 500行の結果でも要約は2,000文字未満（テストで確認） |
| **`inventory_java.py`** | エンドポイントと怪しい箇所の一覧を作る。Claude はフラグの付いたメソッドだけを開く | サンプルでは 7 エンドポイント中、読む対象は 5（設定のフラグは別に3件） |
| **差分モード** | `--changed-since <ref>` で、PR で変更したファイルだけを監査する | 変更量に比例 |
| **作業ファイルの再利用** | `.authz-radar/` の結果を、同じコミット・同じ期間なら使い回す | 2回目以降の問い合わせが不要 |
| **MCP の問い合わせ規則** | 集計だけ、`FACET` は `LIMIT 20` まで、`SELECT *` や生のイベントは取らない | 結果の大きさを抑える |
| **チャットは要約だけ** | 全文はファイルに書き、チャットには上位5件と次の一手 | 出力のトークンを抑える |

トークン数そのものは実測していない（バイト数は実測）。日本語の文章では、おおむね1文字が1トークン前後になる。
