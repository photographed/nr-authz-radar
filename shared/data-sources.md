# New Relic に必要なデータと、それでできること

> 目的（①棚卸し・②利用実態・③攻撃検知・④調査）と段階（S0〜S3）の考え方は `shared/goals.md`。ここはデータソースの詳細。

このプラグインは **「何のデータが入っているか」で見える範囲が決まる**。
まず APM と分散トレーシングで API の実態をつかみ、そこから Browser・Logs・Infrastructure へと見る範囲を広げていく。

Readiness 監査（`skills/nr-appsec-guard/references/readiness-checks.md`）は、この表を上から順に確認する。

## 1. データソースと、それで見えるもの

| 優先度 | データソース | 主なイベント | これで見えるもの | 使う検知・クエリ |
|---|---|---|---|---|
| **必須** | **APM エージェント** | `Transaction`、`TransactionError` | API ごとのアクセス・ステータスコード・ユーザー・例外。**トランザクション名 = API エンドポイント**（§2） | D03、D04、D06、D09、D10、D17、U01、U05 |
| **必須** | **分散トレーシング（APM で有効化）** | `Span` | API の中で実行された SQL 文・外部呼び出し。Browser / Mobile から API までのつながり（`parent.type`） | D07、D08、D12、D20 |
| 推奨（S2〜S3） | **認可属性（コード計装）** | `Transaction` の custom attribute | 誰が・どのスコープで・誰のデータに触れたか。**IDOR 成功を見る唯一の手段** | D01、D02、D05、D11、D13〜D15 |
| 推奨 | **Browser エージェント** | `PageView`、`AjaxRequest`、`BrowserInteraction` | 画面から実際に呼ばれている API（Ajax）の一覧。**正規の画面を通った呼び出しか**の判定 | D12、U02 |
| 任意 | **Logs in context（アプリのログ）** | `Log`（`trace.id`・`span.id` 付き） | **調査の最後の詰めだけに使う**（ラストワンマイル）: 証拠の詳細（L01）、全件化（L02）、属性が送れない場合の代替（L04）。**攻撃を探すログの全文スキャンはしない。無くても検知・棚卸しは動く** | L01・L02・L04、R16 |
| 推奨 | **Change Tracking（デプロイ記録）** | `Deployment` ※要確認 | 異常の直前の変更。「攻撃か、自分たちの変更か」の切り分け。iRCA の精度にも影響 | D18 |
| 任意 | **ミドルウェアのログ**（nginx・Apache・Tomcat のアクセスログ） | `Log` | クエリ文字列を含むリクエスト内容。**APM の `request.uri` にはクエリ文字列が入らない**ため、それを補う | D11 の代替 |

> **Logs の位置づけ（誤解されやすい点）**: このツールは**ログで攻撃を探しません**（ログ全文スキャンは偽陽性が多いため意図的に避けている）。Logs を使うのは、APM で見つけた手がかり（トレース ID・ユーザー・時間帯）を起点に、**調査の最後の詰め**として範囲を絞って取りに行くときだけ（L01〜L04）。したがって Logs は**任意**で、未連携でも検知・棚卸し・調査の中心は動く。「WAF をすり抜けたリクエストをログから探す」のは別の話で、現時点では対象外（`shared/goals.md` の『対象外』を参照）。
| 任意 | **WAF / ファイアウォール / CDN のログ** | `Log` | エッジでの判定（遮断・チャレンジ・bot 判定）。IP 粒度の分析はここに任せる（`shared/privacy.md`） | D11（`edge.verdict` の代わり） |
| 任意 | **OS のログ**（auth.log・syslog 等） | `Log` | サーバーへのログイン、侵入後の操作 | 侵入後の調査 |
| 任意 | **Infrastructure エージェント** | `SystemSample`、`ProcessSample`、`NetworkSample` | CPU・プロセス・通信量。**プロセス情報は既定で無効**のため、必要なら有効化 | 侵入後の兆候 |
| 任意 | **Network Performance Monitoring** | フローデータ（イベント名は要確認） | ホスト間・外部との通信の流れ。**APM に出ない JNDI（LDAP / RMI）や DNS の通信**も含む | D20 の補完 |
| 任意 | **Vulnerability Management** | — | 使っているライブラリの既知の脆弱性 | 予防（A03） |
| 任意（申請制） | **IAST**（Limited Preview。Java は [New Relic Security Agent](https://github.com/newrelic/csec-java-agent)） | — | テスト環境でアプリを実際に動かして脆弱性を検出する。コード監査の Finding の**裏付け**に使う（§4） | コード監査（F7 など）の確度を上げる |

**IAST の注意**: 公式に「本番環境では使わないこと（pre-production のみ）」とされている。

**判断の目安**: 「必須」の2つ（APM と分散トレーシング）が揃っていない状態で検知を増やしても効果は小さい。前提の確認はまずここの不足を指摘する。認可属性は段階的に（まず S2 の2属性）入れる。

## 2. トランザクション名 = API エンドポイント

> REST 以外の方式（GraphQL・SOAP・JSON-RPC・WebSocket）では、トランザクション名ではなく `api.operation` を API の単位にする（`shared/protocols.md`）。

API 単位で認可を評価するには、**1つの API が1つのトランザクション名になっている**必要がある。ここが崩れていると、コード監査との突き合わせも、エンドポイント別の検知もできない。

| 状態 | 例 | 問題 | 対処 |
|---|---|---|---|
| ✅ 良い | `WebTransaction/SpringController/api/v1/orders/{id} (GET)` | — | — |
| ⚠️ まとめられすぎ | `WebTransaction/Servlet/dispatcherServlet` | 全 API が1つの名前になり、API の区別がつかない | フレームワークの計装を有効にする、または API で名前を付ける |
| ⚠️ 細かすぎ | `.../orders/12345 (GET)` | ID ごとに名前が分かれる。名前の種類が多すぎると New Relic 側でまとめられ（metric grouping issue）、読めなくなる | パス変数をテンプレート（`{id}`）のまま名前にする |
| ⚠️ メソッド名だけ | `OrderController/getOrder` | パスと HTTP メソッドがわからず、コードとの突き合わせが難しい | パスベースの命名にする（Java エージェントは設定で切り替えられる。設定名は要確認） |

## 3. API 設計（Ajax を含む）を見る

認可の評価には、API がどこから・どう呼ばれているかという **API 設計の実態** が必要になる。New Relic では、3つの視点を突き合わせて組み立てる。

| 視点 | データ | わかること |
|---|---|---|
| コード | `api-authz-review` のエンドポイント一覧 | 実装されている API と、そのスコープ・所有者照合 |
| サーバー | APM の `Transaction`（U01） | 実際に呼ばれている API と、その量 |
| 画面 | Browser の `AjaxRequest`（U02） | 正規の画面が呼んでいる API |

この3つのズレが手がかりになる。

- **コードにあるが、サーバーで観測されない** → ゾンビ API（または計装漏れ）
- **サーバーで観測されるが、コードにない** → シャドー API
- **サーバーで呼ばれているが、画面からは呼ばれていない** → モバイル・外部連携向けか、**直接呼び出し**（アプリ解析による API の特定。JPCERT-AT-2026-0030 の手口）

## 4. IAST とこのプラグインの役割分担

Java の IAST は [New Relic Security Agent for Java](https://github.com/newrelic/csec-java-agent)。APM の Java エージェントに組み込まれて自動でインストールされ、Java 8 以上で動く。
**本番環境では使わない**（公式の注意書き）。導入手順は New Relic の IAST のドキュメントを参照する。

| 脆弱性 | IAST | このプラグイン |
|---|---|---|
| SQL インジェクション | ✅ 検出対象 | コード監査 F7、実行時の検知 D06〜D09 |
| RCE、リバースシェル | ✅ 検出対象 | コード監査 F9、実行時の検知 D20・D21 |
| 安全でないデシリアライズ | ✅ 検出対象 | コード監査 F10、実行時の検知 D21 |
| NoSQL / LDAP / XPath / XQuery / JavaScript インジェクション、XSS、SSRF、ファイルアクセス、弱い暗号 など | ✅ 検出対象 | 対象外（IAST の結果を参照するよう案内する） |
| **IDOR / BOLA、スコープ不備、BFLA** | ❌ 一覧に無い | ✅ **中心的に対応**（コード監査 F2〜F5、実行時の検知 D01〜D05） |

使い方:
- **テスト環境**: IAST で見つかった脆弱性と、`api-authz-review` の Finding を突き合わせる。両方で見つかったものは `confidence: confirmed` にする。
- **本番環境**: IAST は使わない。このプラグインの実行時の検知（D01〜）で攻撃に気づく。
- IAST で見つからなかったことは、脆弱性が無いことを意味しない（テストで通らなかった経路は検査されない）。

> 上の検出対象は、リポジトリの README（2026-10-23 時点）による。コマンドインジェクション・XXE・パストラバーサルは一覧に明記されていない（「RCE」「ファイルアクセス」に含まれるかは要確認）。
