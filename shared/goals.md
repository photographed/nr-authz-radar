# 4つの目的と、段階的な計装

このプラグインが扱う問題は **4つの別々の目的** に分かれる。答えたい問いも、必要なデータも、カスタム属性の要否も違うので、混ぜずに扱う。

| 目的 | 答えたい問い | 主なデータ | カスタム属性 |
|---|---|---|---|
| **① 棚卸し** | API は全部でいくつあり、それぞれどんな認可設計か | **ソースコード**（`api-authz-review`）。New Relic は補助（U01・U02） | 不要 |
| **② 利用実態** | どの API が、どこから（画面・モバイル・直接）、誰に、どれだけ使われているか | APM の `Transaction`、分散トレーシング（`parent.type`）、Browser の `AjaxRequest` | 不要（ユーザー単位で見るなら S1） |
| **③ 攻撃検知** | 今、攻撃を受けているか | APM・Errors Inbox・`Span`（＋ あれば認可属性） | 大部分は不要。**IDOR 成功の確証だけ S2 が必要** |
| **④ 調査** | 何をされたか、どのデータが取られたか（**200 で返った分も含む**） | **ログ（全件）**＋ APM（手がかり）＋ トレース ID による紐付け | 不要。ただし**記録の網羅性と保存期間**が問題になる |

## 段階（アプリ側の計装をどこまでやるか）

| 段階 | やること | 追加で使えるようになるもの |
|---|---|---|
| **S0** エージェントのみ | APM エージェントを既定の設定で入れる（分散トレーシングが有効か確認） | ② 利用実態のほぼすべて。③ のうち D04、D06〜D10、D12、D17、D18、D20、D21 |
| **S1** 設定のみ | `newrelic.yml` などで `enduser.id` を送る（**生の ID ではなく仮名化が望ましい**ため、実際は S2 と同時に API で送ることが多い） | ユーザー単位の利用実態、D03（ID 列挙）、D13 |
| **S2** 最小限のコード | **`resource.owner_match` と `authz.decision` の2つ**（＋ `enduser.id`。REST 以外の方式は ＋ `api.protocol`・`api.operation`） | **D01（IDOR 成功の証拠）**、D02 |
| **S3** 全属性 | `shared/attribute-spec.md` の残り | D05、D11、D14、D15 |

**どうしても必要なコード計装は S2 の2属性だけ。** 他の属性には代わりの手段がある。

| 属性 | 代わりの手段 |
|---|---|
| `authz.required_scope` | コード監査（`api-authz-review`）で静的に取れる |
| `client.type` | 分散トレーシングの `parent.type`（Browser / Mobile / なし） |
| `client.asn`・`client.ip_hmac` | WAF / CDN の判定、アクセスログ（`shared/privacy.md`） |

逆に、**S2 の2属性が無いと、攻撃が成功した IDOR（他人のデータが 200 で返った）を証拠として見つける方法は無い。** D03（ID 列挙）は「怪しい量」は示せるが、他人のデータだったかは示せない。

## データソース（段階とは別の軸）

段階はアプリ側の計装、データソースは「New Relic に何を入れているか」。両方を見て「今わかること」が決まる。
詳細は `shared/data-sources.md`。

| データソース | 主に効く目的 |
|---|---|
| APM + 分散トレーシング | ①②③④ すべての土台 |
| Browser | ②（画面から呼ばれている API）、③（D12） |
| Logs in context・アクセスログ（任意） | **④（調査の全件化）だけ**。攻撃探索のスキャンはしない |
| Change Tracking | ③（攻撃か自分たちの変更か） |
| WAF・ファイアウォール・OS のログ | ③（エッジの判定）、④（侵入後の操作） |
| Infrastructure・NPM | ③（D20 の補完）、④ |

## ④ 調査で APM だけでは足りない理由

1. **サンプリング**: APM の `Transaction` イベントには保存の上限があり、アクセスが多いとすべては残らない。「攻撃者がどの ID を取得したか」を全件で答えるには、全件が残るログが必要（I05 で確認）。
2. **保存期間**: 気づいたのが数週間後だと、データが既に消えている可能性がある（I06・I07 で確認。期間はプランやデータの種類で異なる）。
3. **保全**: 調査で得た結果は、保存期間が切れる前にエクスポートして残す。

役割分担:
- **APM**: 手がかりを見つける（いつ・誰が・どの API を。`request.uri` で 200 応答の ID も分かる範囲で）
- **ログ**: 全件で確定させる（トレース ID でログに移り、対象のアクセスを洗い出す）

## レポートの書き方（すべての Skill・モードで共通）

**「今のデータでわかること・できること」と「推奨」を、必ず別の節に分ける。** 混ぜると、まだ見えていないことを見えているように読めてしまうため。

```
## 今のデータでわかること・できること
- 現在の段階: S0（エージェントのみ）／ データソース: APM, 分散トレーシング, Browser
- 目的ごとの状況（できる / 一部 / できない、と理由）
- 実行した確認・検知の結果（できなかったものは「判定不能（理由）」）

## 推奨（段階的に）
1. 次の段階に進むための作業（例: S2 の2属性を入れる）
   - これで新たにわかるようになること（例: D01 IDOR 成功の証拠）
   - 対象の目的（例: ③ 攻撃検知）
2. 追加すると効果の大きいデータソース（例: アクセスログ → ④ 調査の全件化）
```

推奨には、必ず **「それをやると何がわかるようになるか」** と **「どの目的に効くか」** を書く。

### 証拠の強さで分ける（偽陽性への対策）

検知の結果は **証拠の強さ**（`shared/detections.json`）ごとに分けて書く。

| 強さ | 書き方 |
|---|---|
| **証拠**（D01・D07、D20 と D21 の同時発生） | 「攻撃を受けている（成功している）」と書いてよい。最初に報告する |
| **強い兆候**（D02・D05・D06・D21・D23） | 「攻撃の試みの痕跡がある」。成功したとは書かない |
| **異常**（D03・D04・D10・D12 など） | 「平常時と違う動きがある」。**攻撃とは書かない。** 他の強さの結果や利用実態と合わせて解釈する |
| リスク・参考 | 攻撃の兆候としては扱わない |

異常だけで「攻撃を受けている」と結論づけない。異常は偽陽性が多い（正当な利用の変化・リリース・キャンペーンでも起きる）。

## 対象外（意図的にやらないこと）

- **ログの全文スキャンによる攻撃探索はしない。** 例: アクセスログの URL・クエリ文字列を `UNION SELECT` 等のパターンで検索して「攻撃の試み」を数える、という SIEM 的な検知。量に比例してコストがかかり、**偽陽性が非常に多い**（正当な入力・ツール・クローラでも一致する）。本ツールは「成功した攻撃をアプリ内部の文脈で確実に捕まえる」方針（D01=IDOR 成功、D07=実行された SQL 文）で、試行のパターン検索は WAF / SIEM の役割とする。
- Logs を使うのは**調査の最後の詰め**（L01〜L04）だけで、APM の手がかりで範囲を絞って取りに行く（`shared/data-sources.md` の「Logs の位置づけ」）。
- WAF をすり抜けてアプリに届いた攻撃は、成功していれば D01・D06・D07・D21 で見える。WAF が遮断した分は D25（件数の把握）と L03（必要な時だけログで詳細）で補う。
