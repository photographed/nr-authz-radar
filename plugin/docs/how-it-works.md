# 仕組みの全体像: IDOR などをどう判定しているか

## 前提: なぜ IDOR は見えにくいのか

IDOR が成功すると、正常なアクセスとまったく同じ **200 OK** が返る。
「返したデータが、要求した人のものだったか」を知っているのは **アプリだけ** で、ログやステータスコードをいくら集めても、この1点は分からない。

そのため、このプラグインは **4つの層** で判定する。層ごとに「どこまで言えるか」の強さが違う。

```
            リクエスト
                │
  ┌─────────────▼──────────────┐
  │ 認証（誰か）                 │ ← D10 認証失敗の急増
  ├────────────────────────────┤
  │ 認可（何をしてよいか）        │ ← D05 スコープ不足（authz.required_scope）
  │  @PreAuthorize / URL ルール  │    コード監査 F1〜F3・F5
  ├────────────────────────────┤
  │ 処理（ハンドラ・リゾルバ）     │
  ├────────────────────────────┤
  │ データ取得 ← ★ここが核心      │ ← 所有者照合: 「所有者 = 要求者か」を比較
  │  findById(id)               │    → resource.owner_match
  │                             │    コード監査 F4（照合が無い箇所を探す）
  ├────────────────────────────┤
  │ 応答                         │ ← authz.decision（allow / deny）
  └─────────────┬──────────────┘
                ▼
     New Relic（Transaction に属性が付く）
```

所有者照合を **データ取得の層** で行うのは、API の方式（REST・GraphQL・SOAP・gRPC・WebSocket）や呼び出し元（画面・モバイル・スクリプト）に関係なく、同じ判定ができるから。

## 4つの層と、それぞれで言えること

| 層 | 何を見るか | 例 | 言えること |
|---|---|---|---|
| **① コード（静的）** | ID を受け取ってデータを取る箇所に、所有者・テナントの照合があるか | F4: `findById(id)` をそのまま返している | **「IDOR の可能性がある」**（穴の存在） |
| **② 実行時・計装なし**（S0・S1） | アクセスの「形」 | D03: 1人が1時間に100種類の ID を取得。D04: 404 の急増。D12: 画面を通らない呼び出し | **「疑わしい」**（他人のデータだったかは分からない） |
| **③ 実行時・計装あり**（S2） | アプリ自身の判定 | D01: `owner_match = false` かつ `allow` | **「他人のデータを返した証拠」** |
| **④ 調査** | ログの全件 | I01〜I04: 対象ユーザーが 200 で取得したリソースを全件洗い出す | **「何件、誰のデータが取られたか（確定）」** |

### 層どうしの関係
- **① は「どこに穴があるか」、③ は「その穴が実際に使われたか」** を示す。① で見つけた F4 の候補に所有者照合の計装を入れると、③ で実際に起きているかが分かる（OBSERVE モードの役割）。
- **② は ③ が無い環境での代わり**。量やパターンから疑いを示せるが、証拠にはならない。
- **優先順位** は ① を主軸にし、②③ の兆候で引き上げる（`shared/risk-scoring.md`）。使われていない API でも、① で重大なら上位に来る。

## IDOR 以外の判定

| 攻撃 | 判定の仕組み | 強さ |
|---|---|---|
| SQL インジェクション | 失敗した試みの痕跡（D06 構文エラー）、SQL 文の形（D07 `UNION SELECT` など）、時間の二山（D09） | D07 は「注入できる箇所がある」証拠に近い |
| RCE | 失敗した試みの例外（D21）＋ 見たことのない外部通信（D20） | 両方そろうと「成功の可能性」 |
| 認証攻撃 | 401 の急増（D10）、1アカウントに多数のネットワーク（D11） | 疑い |
| 自動化（AI エージェントらしい挙動） | 画面を通らない（D12）、一定の間隔（D13） | 疑い。**断定はしない** |

## 証拠の強さと偽陽性

すべての検知に **証拠の強さ** を付けている（`shared/detections.json`）。偽陽性の出やすさは強さによって大きく違う。

| 強さ | 例 | 偽陽性 | 通知 |
|---|---|---|---|
| **証拠** | D01（他人のデータを返した）、D07（注入された形の SQL が実行された） | ほぼ出ない（アプリ自身の判定・実行された事実のため）。出るのは共有・委任・管理者などの例外の設定漏れ | CRITICAL（Autopilot も） |
| **強い兆候** | D02、D06、D21 など | 少ない（正常な利用ではほぼ起きない） | HIGH（導入直後は通知しない） |
| **異常** | D03、D04、D10、D12 など | **多い**（正当な利用の変化でも起きる） | 通知しない（日次で確認） |

IAST が「本番前に、攻撃が危険な処理まで届いたことをアプリの中で観測する」ことで偽陽性を抑えるのと同じく、
「証拠」は **本番のアプリの中で、他人のデータを返したことを観測する**。異常の検知は、この証拠が無い環境での補助にとどめる。

## この仕組みの限界

1. **所有者照合を入れた場所しか ③ で見えない。** 入れ忘れた API は見えないままになる。① コード監査（入れるべき場所の一覧）、R02（属性が付いている API の割合）、XML 計装（照合が実行されたか）の3つで補う。
2. **トランザクションの中で動いていることが前提。** トランザクションの外で属性を送っても捨てられる。WebSocket のメッセージ処理は、多くのエージェントで既定ではトランザクションにならないので、メッセージごとにトランザクションを作る必要がある（`shared/data-sources.md`）。
3. **「所有者」の定義はアプリごとに違う。** 共有・委任・家族アカウントなどは、所有者の判定や除外の設定で合わせる。
4. **ステータスコードを使う検知は REST 前提。** GraphQL は拒否しても 200、SOAP は 500 を返すことが多い。REST 以外では、認可判断（`authz.decision`）を使う検知を使う。
